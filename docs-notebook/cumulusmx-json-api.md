# The CumulusMX local API

This page records what `CumulusMXWeatherClient` depends on, what the rain work will
depend on, and where each fact came from.  The facts come from CumulusMX's `main`
branch, the version 5 line the operator's station runs, as it stood on 2026-09-28, and
from the Cumulus wiki.

The first reading, on 2026-09-27, fetched `master` from GitHub's raw file service.  The
repository has no branch of that name any more, and what came back was a version 3
snapshot whose `Updates.txt` ends at 3.28.6.  Every fact below was checked again against
`main` on 2026-09-28, and each held, apart from the two differences noted where they
arise.  The live checks ran against the operator's Davis
Vantage Pro2, which reports imperial units and rolls its day over at midnight.

## Two ways to ask

CumulusMX serves webtags through two endpoints, and they differ in what a tag can be
told.

The JSON API is a GET to `http://host:port/api/tags/process.json?rc&temp&hum&...`.
`ApiTagProcessor.ProcessJson` splits the query on `&`, treats each item as a webtag
name, and returns every value as a JSON string: `{"temp":"57.7","hum":"85",...}`.  It
builds each tag's parameters from `rc` alone, so no other parameter can reach a tag.
The client uses this endpoint today.

The text API is a POST to `http://host:port/api/tags/process.txt`, with a template as
the body.  `ApiTagProcessor.ProcessText` runs the body through the same token parser
as CumulusMX's own web templates, so every tag parameter works.  On 2026-09-27 the
operator's station answered this body:

    {"t":"<#LastDataReadT format=Unix>","now":"<#timeUnix>","temp":"<#temp rc=y>",
     "tempC":"<#temp unit=c rc=y>","wspeed":"<#wspeed rc=y>","wspeedKph":"<#wspeed unit=kph rc=y>"}

with `{"t":"1790546601","now":"1790546601","temp":"65.2","tempC":"18.4","wspeed":"11","wspeedKph":"17"}`.
A template that is itself JSON gives a JSON answer, so the client can parse either
endpoint's reply the same way.

## Units come from the station

CumulusMX serves every figure in the station's own units.  The client asks for the
`tempunitnodeg` and `windunit` webtags and converts from what they name.

- `tempunitnodeg` returns `TempText.Substring(1, 1)`, where `TempText` is `°C` or
  `°F`.  It can only be `C` or `F`.
- `windunit` returns `Units.WindText`, which `Cumulus.cs` sets from the station's
  `WindUnit` setting.  The values 0 to 3 give `m/s`, `mph`, `km/h` and `kts`.  Any
  other value leaves the text unset, and the client refuses it.
- `rainunit` returns `Units.RainText`, which is `mm` or `in`.

Those are the only strings the client accepts, so a metric station needs no test of
its own.  The operator's station cannot switch to metric without damaging its
database, so the source is the only check there is.

## The unit parameter reaches the text API only

`webtags.cs` converts units on request.  `CheckTempUnit` takes `unit=c` or `f`,
`CheckWindUnit` takes `unit=mph`, `kph`, `ms` or `kt`, and `CheckRainUnit` takes
`unit=mm` or `in`.  The wiki page the operator read on 2026-09-22 does not mention it.
CumulusMX's `Updates.txt` dates it to version 3.23.0, build 3220: "Most weather value
web tags now perform unit conversion."  The operator's station runs 5.1.5, build 5012.

The JSON API cannot pass the parameter, and the text API can.  An earlier version of
this page said no API could, which was wrong.

On 2026-09-27, with the client already on the text API, the operator decided to keep
reading the station's own units and converting them, rather than asking for `unit=`.
There were three reasons:

- A CumulusMX older than 3.23.0 ignores the parameter and answers in the station's own
  units, with nothing in the reply to say so.  That writes Celsius under a Fahrenheit
  heading, the fault the units work set out to fix.  Reading `tempunitnodeg`,
  `windunit` and `rainunit` from the same reply checks itself instead.  A guard would
  have to ask for `<#build>` and refuse anything under 3220.  Build numbers rise across
  major versions, with version 3 ending near 3283 and version 5 in the 5000s, so that
  guard would work, at the cost of trusting a version number over the reply.
- `CheckRcDp` rounds a converted figure to the station's configured decimal places
  unless the template also passes `dp=`.  The operator's station returned 11 mph as
  `17` km/h, with no decimals at all, so every converted tag would need `dp=2` too.
  `Updates.txt` gives the same warning.
- The client keeps conversion code anyway, because a CSV file keeps the units it
  started with.  Asking CumulusMX to convert would have saved about twenty lines.

What it would have gained is a slightly finer figure.  CumulusMX converts its own
unrounded value, where the client converts one already rounded to the station's
decimal places.  At one decimal of a degree Fahrenheit, the difference is below
anything this program reports.

## The time of the data

`LastDataReadT` is the time CumulusMX last received a packet from the station.
`WeatherStation.UpdateStatusPanel` sets it, and on the operator's station it advanced
every few seconds, one Davis packet at a time.

Its default format is .NET's `"G"`, which follows the host's locale and carries no
zone: the operator's station returned `"9/27/2026 3:02:51 PM"`.  A German host would
put the day first.  A local time without an offset is also ambiguous for one hour each
year, when clocks fall back.  The tag accepts `format=Unix`, which gives epoch seconds,
but only the text API can pass it.

No tag reports the host's timezone or offset.  `timeUTC` is the current UTC time as
display text, and nothing else in `webtags.cs` names a zone.  The offset can be
derived by asking for `timeUnix` and `timehhmmss` in one request and taking the
difference.  On `main`, `timeUnix` is `DateTime.UtcNow.ToUnixTime()`, a true UTC
epoch, and `timehhmmss` is `DateTime.Now.ToString("HH:mm:ss")`, the host's local
clock.

The derivation worked against the operator's station on 2026-09-28.  CumulusMX 5.1.5,
build 5012, answered `timeUnix` 1790648948, which is 02:29:08 UTC, and `timehhmmss`
19:29:08.  The difference is -25200 seconds, or -7 hours, which matches
`America/Los_Angeles` on that date.  UTC had already passed midnight there while local
time had not, so the day wrapped, and the arithmetic has to take the difference modulo
24 hours.  Rounding to a quarter hour absorbs a second that ticks between the two
readings, and still tells apart the zones that sit on half and quarter hours.

## Rain

The rain webtags, from `webtags.cs` and `WeatherStation.cs`, all in the unit
`rainunit` names:

- `rmidnight` is rain since midnight.  `ResetMidnightRain` zeroes it when the date
  changes, by the date of the timestamp CumulusMX passes it.  Midnight is the host's,
  as far as the code shows, which matches the station only when the host's clock is set
  to the station's zone.
- `rfall` is rain since CumulusMX's day rollover, which can be midnight, 9 am or
  10 am.  The `rollovertime` tag says which.  The operator's station reports
  `midnight`.
- `rhour` and `r24hour` cover the last hour and the last 24 hours.
- `rrate` is the current rate.  CumulusMX computes a five-minute rate itself only
  for a station that does not report one.  A Davis console reports its own, which the
  Vantage Pro2 console manual bases on the time between 0.01" bucket tips, reading zero
  until two tips fall within 15 minutes.  That manual was read through a search
  summary, because the PDF did not extract.

All five pass through `CheckRcDp`, so `rc` covers them.

## Decimal commas

`CheckRcDp` formats temperature, wind and rain with `val.ToString("F" + dp)`, which
follows the host's current culture.  `Program.cs` sets a culture only when CumulusMX
starts with `-lang`.  So a station on a German or French machine serves `"20,5"`,
and `float()` refuses it.  Humidity, solar radiation and bearing are integers, and
never carry a decimal separator.

The wiki's local API page documents the fix: "You can specify a special parameter
"rc" (which must be the first URL parameter) to apply the usual remove commas format
to all the tags."  In the code, a leading `rc` gives every tag `rc=y`.  On `main`,
`CheckRcDp` then formats the figure in the invariant culture, where version 3 replaced
each comma with a period.  Both give a period.  Anywhere after the first position, `rc`
is read as a tag.  In the text API, `rc=y` goes on each tag in the template instead.

Version 5 added one behavior the client has to handle.  A tag whose sensor has no
reading returns `"-"`, or whatever the tag's `nv` parameter names, where version 3
returned a number.  `SolarRad` does this on a station with no solar sensor, and about
a hundred tags in `webtags.cs` on `main` can.  The client passes solar radiation
through as text, so such a station writes `-` in that column instead of leaving it
blank.  `todo.md` carries the fix.

The client puts `rc` first.  On 2026-09-27 the operator's station, which writes
periods already, returned the same JSON with and without it, and did not echo `rc` as
a key.  No comma-locale station has been tried.
