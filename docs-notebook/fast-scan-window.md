# The Tier-3a screening window, and what it measures at other sample rates

Found and fixed on 2026-09-13, while deriving magic constants rather than writing
them out.  The window is fixed now.  The threshold it feeds is not, and the numbers
below are here so that whoever takes that on does not have to measure it again.

## What was wrong

`FAST_SCAN_SAMPLES` was the literal 4000, described in its comment as "~0.25 s at
16 kHz".  The kernel it has to hold is built from the sample rate and the pulse rate,
so it grows while the window stood still.  Past about 34 kHz at 120 pps, or 28.5 kHz
at 100 pps, the kernel no longer fitted inside the window.

Nothing raised.  `scipy.signal.fftconvolve` accepts `mode='valid'` with either
argument longer than the other and returns the other arrangement, so
`calculate_pps_fit_array` gave back a full array of scores taken by sliding the data
along the kernel rather than the kernel along the data.  A direct correlation over
the same inputs has no valid positions at all:

    rate     kernel   window   fft scores   direct scores
    16000      1870     4000         2131            2131
    32000      3736     4000          265             265
    44100      5148     4000         1149               0
    48000      5603     4000         1604               0

Tier 3a compares the peak/trough ratio of that array against `FAST_SCAN_SNR` to decide
whether re-acquisition escalates to the full FFT.  Above those rates it was deciding on
a number with no meaning, over 34% of the legal 8 to 48 kHz band at 120 pps and 49% at
100 pps.

## The fix

The quantity somebody actually chose is in the pulse domain, not the sample domain:

    FAST_SCAN_WINDOW_PULSES = 2 * FAST_SCAN_PULSES

The kernel spans `FAST_SCAN_PULSES` of those periods and the rest is room to slide it.
At 16 kHz and 120 pps this comes to exactly 4000, so a station at the default saw no
change at all.  Across the whole band the window never leaves fewer than 1064 valid
positions, against the 2 the fit needs.

`tests/test_continuous_analyzer.py::TestTheFastScanWindowFollowsTheSampleRate` walks
the band at both grid frequencies and pins the FFT path against a direct correlation
at 48 kHz, which is where the two used to disagree.

## What is still wrong

`FAST_SCAN_SNR = 8.0` does not transfer across sample rates, and the fix above does
not change that.  The statistic is the ratio of the largest to the smallest score in
the fit array, so a longer array gives the extremes more chances and the noise-only
floor rises with it.  Measured over 60 windows of Gaussian noise at each rate, with
the derived window:

    rate     window    mean dB    max dB    fires on noise?
     8000      2000       5.89      7.37    no
    16000      4000       6.37      7.61    no
    32000      8000       6.93      8.91    yes
    44100     11025       7.08      8.44    yes
    48000     12000       7.05      8.74    yes

The 16 kHz row reproduces the figures already in the `FAST_SCAN_SNR` comment, 6.4 dB
mean and 7.6 dB maximum, which confirms those were measured at 16 kHz with this
window.

From about 32 kHz upward, noise alone crosses the threshold.  Tier 3a then fires on
every call and escalates to the full FFT anyway, so it stops saving anything and
becomes pure overhead.  That is the same failure the threshold had at every rate when
it was 4.0, described in the comment beside it.

It is left alone deliberately.  A threshold derived from the array length would fix
it, and nothing has run this program at those rates in anger, so there is no
measurement of what a real signal scores there to check a new threshold against.  The
station this was written for runs at 16 kHz, where the figures hold.

## How the numbers were taken

Windows of `np.abs(rng.standard_normal(n))` as the noise-only input, 60 per rate, the
same kernel the analyzer builds, and the peak/trough ratio `_fast_scan` itself
computes.  Gaussian noise is not band-limited receiver noise, so treat these as the
shape of the effect rather than as the exact floor a station would see.
