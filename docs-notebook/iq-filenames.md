# How SDR programs find an IQ recording's frequency

The operator ran these tests on 2026-09-28, with a Windows PC and an SDRplay RSP.  The
question was how to name an IQ recording so that SDR programs open it at the right
center frequency.  The answer is a name that contains the frequency twice:

    event_IQ_20260928_154116-0700_3590000HZ_3590000Hz.wav

That name opened at the right frequency in SDRconnect and in SDR#.  SDR++'s source shows
that it reads the name correctly too.

## Nothing inside the file says the frequency

Two search summaries claimed that SDRconnect reads, and SDR# writes, an `auxi` chunk in
the WAV file holding the center frequency.  They gave a layout for it that contradicted
itself about the chunk's size.  Both claims were false.  A dump of each program's own
recordings found these chunks, and nothing else:

| program | container | chunks |
|---|---|---|
| SDR# | `RF64` | `ds64` (28 bytes), `fmt `, `data` |
| SDRconnect | `RIFF` | `JUNK` (28 bytes of zeros), `fmt `, `data` |

SDRconnect's `JUNK` chunk is the size of a `ds64` chunk.  That is the usual way for a
writer to reserve room to turn a file into RF64 in place, if a recording passes 4 GB.

So each program's only record of the frequency is the filename it writes:
`17-39-56_124410001Hz.wav` from SDR#, and
`SDRconnect_IQ_20260928_184240_124156789HZ.wav` from SDRconnect.

SDRconnect's files also have a `data` chunk that claims 36 bytes more than the file
holds: 14,001,156 claimed against 14,001,120 present, and 13,601,124 against 13,601,088.
SDR# refuses to open them for that reason.  So SDRconnect's layout is no model for this
program's own files.

## SDRconnect

SDRconnect ignored the frequency in SDR#'s filename, and showed the monitor's own
recordings centered on 128 kHz.  That is where a 256 kHz capture sits when a program
takes it as baseband starting at 0 Hz.  The operator then renamed one of SDRconnect's
own recordings and opened each copy.  A different frequency in each name showed which
one SDRconnect read:

| name | result |
|---|---|
| `SDRconnect_IQ_20260928_184240_124156543Hz.wav` | no frequency |
| `SDRconnect_IQ_20260928_184240_124156765HZ.wav` | read |
| `SDRconnect_IQ_20260928_184240_124156789HZ_IQ.wav` | read |
| `SDRconnect-IQ-20260928-184240-124156789HZ.wav` | no frequency |
| `DERP_20260928_184240_124156789HZ.wav` | no frequency |
| `DERP_IQ_20260928_184240_124156789HZ.wav` | read |
| `DERP_IQ_20260928T184240_124156789HZ.wav` | no frequency |
| `DERP_IQ_20260928_184240-0700_124156789HZ.wav` | read |

The operator also confirmed that a name without `IQ` in the second field is not read.
The rule that fits every result is that SDRconnect splits the name on `_`.  The second
field must be `IQ`, and the fifth must be the frequency ending in capital `HZ`.  The
first field can be anything, a field after the fifth is ignored, and the fourth may
include a UTC offset.  Whether SDRconnect reads the date and time fields at all, or only
counts them, was not tested.

`HZ` is the wrong symbol, since the hertz is written `Hz`, and SDRconnect requires it.

## SDR++

SDR++ reads the frequency in `getFrequency`, in
`source_modules/file_source/src/main.cpp` on its `master` branch as of 2026-09-28:

    std::regex expr("[0-9]+Hz");

It takes the leftmost match anywhere in the name and returns 0 when there is none.
`std::regex` matches case-sensitively, so SDR++ never reads SDRconnect's `HZ`.  No
single token can therefore satisfy both programs, which is why the name contains the
frequency twice.  In the name at the top, the leftmost match is the second token,
because the first ends in `HZ` and none of the timestamp's digits are followed by
`Hz`.

## SDR#

The operator had already found that SDR# reads a frequency ending in `Hz` from the name,
as in its own `17-39-56_124410001Hz.wav`.  It also opened the name at the top at the
right frequency.  Its exact rule is unknown.  Both tokens hold the same number, so
SDR# gets the right answer whichever one it reads.

## The frequency in the name

The frequency has to be the tuned one, not the listening one.  The monitor tunes the
receiver `tuning_offset_hz` above the frequency it measures, 50 kHz by default, and
the capture is centered on the tuned frequency.  Listening on 3540 kHz, the name
contains 3590000.  A program given the listening frequency would label every signal
50 kHz off.

## The audio recording keeps its name

On 2026-09-30 the operator chose to leave the audio recording's name as it was,
`event-20260928-154116-0700.wav`, when the IQ name changed.  Only SDR programs need
the new layout, and nothing opens the audio file in one.  The old name also keeps
working for anything that already matches on it, such as the batch renderer's output
names.  The two files of one event no longer look alike, but both contain the same date,
time and UTC offset.

`IqEventRecorder.is_iq_capture` still recognizes the `-iq.wav` name that 2.0.0 and
2.1.0 wrote, because a recording directory keeps files from every release.
