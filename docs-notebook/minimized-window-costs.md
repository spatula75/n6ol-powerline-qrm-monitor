# Windows slows the monitor when its window is minimized

Minimizing the main window made the whole process slower.  Chart rendering took about
four times as long, and the SDRplay delivery backlog crossed 100 ms several times per
minute.  An explicit Windows HighQoS request removed both effects while the window
remained minimized.

This matters because the monitor runs unattended all day, and minimizing the window is
the obvious thing to do with a program nobody is watching.

## What was measured

Date: 2026-09-18.  Windows 11, with an SDRplay RSP1B feeding the monitor.  Chart figures
come from the timing line in `buzz.plotter._gc_guarded`.  Backlog figures come from
`SdrplayDevice._report_the_worst_backlog`.

Before the HighQoS test:

| State | Chart render time | SDRplay backlog |
|---|---:|---|
| Window on screen | about 300 ms | no 100 ms crossings |
| Window covered by another window | as fast as on screen | no observed change |
| Window minimized | as much as 1150 to 1400 ms | several 100 ms crossings per minute |
| Headless | as fast as on screen | no observed change |

Stopping the display repaint timers while minimized did not remove the slowdown.  A
separate Qt window that did no work beyond repeated 1 ms sleeps also kept the same sleep
resolution while visible and minimized.  Those tests rule out display painting and a
loss of timer resolution as the cause of the measured delay.

## The HighQoS intervention

A scratch diagnostic called `SetProcessInformation` for both processes in the running
monitor's Python process chain.  It selected `ProcessPowerThrottling`, controlled only
`PROCESS_POWER_THROTTLING_EXECUTION_SPEED`, and cleared that bit.  It did not change
process priority or the timer-resolution policy.

Windows accepted both calls.  With the window still minimized, two chart renders moved
from 936 ms to 253 ms and from 1049 ms to 266 ms.  The SDRplay reported no backlog
crossings past 100 ms in the next interval.  Task Manager priority changes had produced
no visible effect, and Task Manager did not show Efficiency mode as enabled.

The intervention changed one policy and immediately changed both symptoms in the
predicted direction.  This is strong evidence that Windows' automatic execution-speed
QoS for the minimized window caused the slowdown.

## Why the earlier controls did not rule this out

Windows classifies a window-owning process from the window's state.  Microsoft documents
minimized or fully occluded windowed applications as Low QoS, while a process can also
receive a QoS level through other heuristics.  A headless process therefore does not
provide the same control as a minimized window-owning process.  The observed covered
window stayed fast, so either Windows did not classify that window as fully occluded or
another detail of its automatic classification differs from the simplified table.

Task Manager's process priority is also a separate control.  QoS can affect processor
frequency and core selection even when ordinary scheduling priority stays unchanged.
Efficiency mode explicitly requests EcoQoS, but the absence of that label does not turn
off Windows' automatic visibility classification.

The 1 ms sleep experiment tested the other power-throttling bit.  Windows can ignore a
process's timer-resolution requests when its window is minimized, but the monitor kept
its measured sleep resolution.  That result said nothing about execution-speed QoS.

## What changed

`buzz.windows_qos.keep_execution_speed_while_hidden` now makes the same request during
monitor startup on Windows.  It clears only the execution-speed throttling bit for the
current process.  Other platforms return without loading a Windows library.  A failed
request warns the operator and leaves the monitor running, because keeping the window
visible or running headlessly avoids the measured slowdown.

A fresh monitor run with this startup hook kept chart times low while its main window
was minimized.  This confirms that the program's own call reproduces the scratch
diagnostic rather than depending on how the external process was opened.

`MainWindow.changeEvent` also stops the display's repaint timers while the window is
minimized and starts them when it is restored.  This does not solve the Windows QoS
fault.  It remains because running display arithmetic for a window nobody can see wastes
CPU.  Each widget reads the newest audio when it repaints, so the restored display shows
the present rather than replaying missed frames.

## Two reading errors to avoid repeating

The first reading blamed state accumulating inside the process.  The argument was that
after a restart the chart drew from more data and was three times faster, so the data
could not be the cause.  That controlled for one variable out of two: the window had
been minimized before the restart and was on screen after it.

The second reading blamed the display competing for the GIL, but a minimized window
paints less.  That explanation predicted the opposite direction before any mechanism
was proposed.

The object count also moved from about 9000 to about 14600.  A generation 0 pass sweeps
everything allocated since the last one by any thread.  A render that takes four times
as long gives the audio and analysis threads four times as long to allocate into the
same generation, so the count was an effect of the delay rather than its cause.
