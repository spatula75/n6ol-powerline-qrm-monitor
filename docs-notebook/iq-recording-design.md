# Raw IQ event recording: design

**2026-09-13.** This is the design worked out before writing any of it.  The goal:
alongside the existing audio event recording, optionally capture the same event's raw
IQ to a second `.wav`, stereo, I on the left channel and Q on the right, for sharing
with someone who wants to do their own signal processing on it.  Playback of an IQ
file through this program is out of scope on purpose.  Nothing here reads one back.

## How much of this is built

**2026-09-14.** The split is done.  `RecordingTrigger` owns every decision and
`AbstractEventRecorder` owns the mechanics of writing one file, with
`AudioEventRecorder` the only subclass so far.  All three live in
`lib/buzz/recorder.py`.

The raw IQ buffer is built too - `IqRingBuffer` in `lib/buzz/sdr.py`, filled by
`RtlSdrPipeline` and gated on the new `[recording] record_iq` - and `IqEventRecorder`
reads it.  An event on a receiver with the setting on now writes two files.

Building the second recorder turned up three assumptions in the abstract base that
had only ever held because audio was the only format: `_emit` cast to `<i2`, the
held-back tail started as a flat array that cannot concatenate with stereo frames,
and the fade ramp raised rather than broadcasting against a row per frame.  None of
them was visible until something other than mono int16 arrived, which is the argument
for the second format being real code rather than a planned one.

The publish/subscribe decoupling is built too.  `RecordingTrigger` holds a list of
`RecordingListener`, a Protocol it satisfies structurally rather than by inheritance,
and `build_recording` is the factory that subscribes whichever recorders the
configuration calls for.  The trigger names no recorder and no format.

It publishes three signals rather than the two this document argued for, and the
reason is the one the two-signal argument rested on: a recorder pulling from its own
buffer on its own schedule needs no signal in between, but it only has a schedule of
its own if it has a thread of its own, and the recorders do not.  Without one, the
trigger's poll is the only clock, so "more has arrived, take what you need" has to be
said out loud.  That is the same thing `RingBufferPipeline._append` already says to
everything waiting on its condition, which makes three signals the honest count until
a recorder owns a thread.

Failure isolation is now the live question rather than a future one, because there
really are two recorders.  A recorder that cannot open its file still disarms the
trigger rather than being skipped, so a full disk on the IQ side takes audio
recording down with it.  Publishing did not change that on its own: `begin` still
reports the name it opened, or None, and the trigger still reads the answer.  What
publishing did change is that a listener which *raises* no longer stops the others,
which is a different failure from one that declines.

What the split already bought is the part that could not be retrofitted later: one
budget, spent once per event by the trigger, whatever number of files an event
produced.

## What the fused version looked like, and the one real gap

Before the split, `EventRecorder` was a single state machine: lock tracking,
`min_lock_seconds`/`min_lock_snr` gating, the event budget and rearm cycle, and the
mechanics of reading a span from the ring buffer, fading, writing, and tagging the
file, all one class, one pipeline, one thread.

Nothing yet keeps raw IQ past the instant it is converted to audio.
`RtlSdrPipeline._consume` converts each block and appends only the audio to the
shared ring buffer; the raw bytes (`IqBlock.raw`) go out of scope immediately after.
An IQ recording's lead-in needs the same thing the audio recording's lead-in gets for
free: a ring buffer already holding the last several seconds when the lock happens.
That buffer does not exist yet and is the one real new piece of infrastructure this
needs.  Everything else is a matter of splitting up code that already works.

## The shape: a trigger that decides, and recorders that write

Two recorders sharing a base class was the starting instinct, and it survived, but
not as two independent state machines.  The reasoning that changed it:

**A shared trigger, not two independent budgets.** Two full state machines fed the
same lock ticks would almost never disagree, since they see the same inputs, but
"almost never" is not "never" - a recorder whose file failed to open counts differently
against its own budget than one whose did not, and the two files could end up
disagreeing about how many events each has recorded.  A single trigger owning the
budget, the rearm cycle, and the decision of *why* an event ended, published once,
removes the question rather than making it merely unlikely.

**Publish/subscribe, the same shape `ContinuousAnalyzer` already uses.** The trigger
does not hold a list of recorder objects and call named methods on them.  It publishes to
whatever is listening, the same relationship `add_state_listener` already has with
every one of its consumers - the analyzer does not know `EventRecorder`, the
waterfall, or the collector exist, and the trigger should not know what a recorder is
either.  This is not a stylistic preference: it means the trigger module has zero
dependency on any concrete recording format, so a future consumer that is not even a
`.wav` writer - a counter, a light, whatever - could listen without the trigger
changing at all.

**Two published events, not three.** The first design had `begin`/`capture`/`finish`,
mirroring the fused class's `_begin`/`_capture`/`_finish`.  Tracing it through, the
`capture` event turned out to carry nothing a listener could not already get for
itself: a published event should carry the fact, never the data, exactly as
`AnalyzerState` carries the state and nothing else and lets a listener go read
whatever it needs.  Once a recorder is trusted to pull from its own pipeline on its own
schedule between two lifecycle signals, the middle event has nothing left to do.  So:

- `begin(started_at, lock_age_seconds)` - `lock_age_seconds` is the one number that
  has to cross the boundary, because only the trigger, listening to the analyzer,
  knows when the lock actually started.  A recorder turns it into its own lead-in position
  by multiplying against its own sample rate.  That multiplication, rounded
  independently per recorder, is the entire source of any disagreement between the two
  files - never more than a sample or two, and never a disagreement about *why* or
  *whether* something happened, only about the exact sample it fell on.
- `finish(reason)` - `capped`, `timeout`, `operator`, or `shutdown`, decided once,
  centrally, the same four reasons `_end_description` already names.

**Why `begin` must return fast and `finish` does not have to.** `CLAUDE.md` already
states the rule this leans on: a listener must not block, because real work belongs
on the consumer's own thread, not the publisher's.  What follows `begin` is unbounded
work - reading and writing for however long the recording runs, possibly two
minutes - and running that on the trigger's own thread would stall it and every other
recorder for the whole recording.  So a recorder's `begin` handler does the minimum: spin up
its own worker thread (reading its own pipeline, writing its own file, on its own
`POLL_INTERVAL` cadence) and return immediately.  The trigger never touches audio data
at all now, not even the reference pipeline's - the state it needs to decide
`min_lock_seconds`/`max_seconds`/`stop_after_seconds` is entirely `total_samples`, a
cheap monotonic counter, never `read_from()`.

`finish` is a different kind of call: bounded, one-time, milliseconds of work - stop
the loop, one last read, fade out, close, tag.  That is not the unbounded work the
rule exists to keep off the publisher's thread, so a recorder's `finish` handler can be an
ordinary synchronous call: signal its own background thread to stop, join it - fully
private to the recorder, invisible to the trigger - then do the final write.  The trigger
calls `finish` on every listener and, by the time the call returns, that recorder is
completely done.  No queue, no thread handle, no join, anywhere in the trigger.

This is what removes the shutdown problem that looked hard at first.  `EventRecorder`
was going to need to track and join every recorder's worker thread before the process
could safely exit, which reintroduces exactly the coupling the whole design exists to
avoid.  It does not need to.  Stopping mid-recording is not a special case: `stop()`
just fires `finish('shutdown')` through the same path as any other reason, and every
listener's own synchronous handler has already closed and tagged its file by the time
that call returns.

**Failure isolation.** If a recorder's file fails to open - a full disk, a bad
`record_iq` directory - it logs and skips that event rather than disarming the
trigger or any other recorder.  A broken IQ path should not take audio recording down with
it, or the reverse.  This is a real behavior change from today's single-recorder code,
which disarms the whole thing on a write failure; with two independent formats now
possible, one failing silently for the other is the wrong trade.

## Format, per source

- RTL-SDR: stereo, 8-bit unsigned PCM, no normalization.  The device already delivers
  unsigned bytes centered near 128, which is exactly what 8-bit PCM `.wav` expects -
  the file is the raw USB bytes with a header, no conversion at all.
- A future 14-bit device (the SDRplay entry in `todo.md`) gets its own subclass
  writing 16-bit signed PCM, matching *its* source rather than a single format chosen
  now for hardware that is not here yet.
- Audio keeps its existing mono, existing 5 ms fade, and whatever future
  normalization gets added is a separate question for that recorder alone.  The IQ
  recorder gets no fade at all - the file is exactly what was captured, which is the
  same reasoning as "no normalization" applied to the edges as well as the levels.

## The ring buffer

`RingBufferPipeline`'s `CHUNK_SIZE` (a class constant, sized for the analyzer's FFT
windows) and two defensive empty-array literals (hardcoded `dtype=np.int16`) are the
only things stopping it from serving as the IQ buffer directly.  Nothing reads the IQ
buffer by chunk count, so `CHUNK_SIZE` becomes a constructor parameter, default 512,
unchanged for every existing caller; the dtype becomes `self._dtype`, default
`np.int16`.  Everything else - `_append`, `read_from`, `capacity_samples`,
`total_samples` - is already dtype-agnostic.

`RtlSdrPipeline` gains a second buffer instance, appended to from `_consume` alongside
the audio conversion, holding the raw `uint8` bytes directly rather than anything
derived from the `complex128` conversion.  One raw block (`DEFAULT_BLOCK_SAMPLES`,
16,384 samples) is appended whole - nothing needs the leftover-holding logic
`_append_in_chunks` uses for audio, since nothing reads the IQ buffer by a fixed
chunk count the way the analyzer reads audio.  Sized to the same `_BUFFER_SECONDS`
(9.6 s) as the audio buffer.

**Built only when `[recording] record_iq` is on.**  An earlier draft of this document
leaned the other way, on the grounds that 4.7 MB at the default rate is too little to
bother gating.  That reasoning only looked at the default.  `iq_sample_rate` has no
maximum in the schema, and the same 9.6 seconds costs 18.8 MB at 1.024 MHz and 43.9 MB
at the 2.4 MHz the hardware accepts, none of it touched by a station that will never
record IQ.

The gate is `record_iq` alone, and deliberately not `[recording] enabled`.  That second
flag does not mean recording is off, it means recording starts disarmed, and the
toolbar can arm it at any point in the run - `main.py` builds the recorder whether or
not it is enabled for exactly that reason.  Skipping the buffer on it would hand an
operator who presses Record an audio file with a full lead-in and an IQ file with
none, which is the two files disagreeing about one event.  Building it lazily on the
first arm fails the same way, because the buffer would start empty and the lead-in is
the whole reason it exists.

## Naming, config, metadata

- `event_filename(when, suffix='')` gains an optional suffix, so the IQ file is
  written as `event-<timestamp>-iq.wav` beside `event-<timestamp>.wav` - same lock
  instant, same `unique_path` collision handling, obviously paired at a glance in one
  directory.
- Config: `[recording] record_iq = false`.  It went there rather than into
  `[rtlsdr]`, where an earlier draft put it, for two reasons.  It is a recording
  setting, and `[recording]` is a full menu in the setup program, so that is where an
  operator looks for one.  And the `[rtlsdr]` menu is deliberately a four-step
  procedure - frequency, gain, check, level - which a fifth unrelated item would
  interrupt.  It carries an `x-visible-when` reaching into `[audio] source`, so a
  sound-card station never sees it.  That is the second cross-section gate in the
  schema, and `tests/test_setup_schema.py` keeps an allowlist of them precisely so a
  third has to be argued for.  `[recording]`'s existing budget and timing fields apply
  to both recorders unchanged, since the trigger they configure is the only thing that
  reads them.
- The IQ file's tags carry what the audio file's cannot: center frequency, IQ sample
  rate, tuner gain, tuning offset, decimation, bandwidth, sideband - read at record
  time, so a mid-run gain change is captured accurately per file rather than as
  whatever the config said at startup.

## What stays the same on the outside

`EventRecorder` keeps its current name, constructor signature, and public methods -
`arm`, `disarm`, `toggle`, `status`, `start`, `stop`.  Internally it becomes one
trigger plus a list of recorders the constructor builds from config: an audio recorder
always, an RTL-SDR IQ recorder only when the source is RTL-SDR and `record_iq` is on.
`main.py` and `RecordingBarWidget` need no changes for "one shared control" - it
falls out of the composition rather than needing new wiring at the call sites.

## Left to settle while building

- `RecorderStatus` currently reports a single `filename`.  With the trigger owning no
  file itself, that has to come from somewhere - either the status stops naming a
  file and the toolbar asks the audio recorder directly, since it always exists, or
  `RecorderStatus` grows a small per-recorder breakdown.  UI-only, does not touch the
  recording logic.

## What the buffer counts

`IqRingBuffer` stores one complex sample per row, as a `(N, 2)` array of unsigned
bytes, rather than the flat interleaved bytes the device delivers.  The first attempt
appended them flat and was wrong in a way that would not have shown up until an IQ
recording had a lead-in half the length of its audio one: `_append` counts
`len(chunk)`, which for interleaved bytes is two per complex sample, while the
capacity the buffer was sized to counts one.  The two would have been in different
units, and every duration derived from them wrong by a factor of two.

A row per complex sample also turns out to be the frame layout a stereo recording
writes, I then Q, so the recorder can hand the rows straight to `wave` without
reshaping them back.

## Testing

The trigger and the recorders split along the same seam the design does, and each is more
testable in isolation than the fused class was.  The trigger can be tested against a
fake listener - asserting *when* `begin`/`finish` are called and with what, no file
I/O at all.  A recorder can be tested against a direct call sequence - `begin`, wait, tell
it to `finish`, read the file back - independent of any lock-timing logic.  Today's
`test_recorder.py` retargets at the audio recorder through the same seam, with no
behavior change expected there.

## Alternatives considered and rejected

- **Two fully independent recorder instances**, each with its own budget and timing
  state, kept in lockstep by whoever owns them.  Simpler to build, much more code
  overall, and leaves open exactly the divergence a shared trigger removes outright.
- **The trigger holding concrete recorder objects and calling named methods directly**,
  rather than a generic listener list.  Works, but ties the trigger module to knowing
  what a recorder is, which the pipeline-to-`ContinuousAnalyzer` relationship already
  shows is unnecessary.
- **A third `capture` event, published every tick.** Removed once it was clear a recorder
  pulling from its own pipeline on its own schedule needs nothing from the trigger in
  between `begin` and `finish`.  Dropping it is also what lets the trigger's own state
  shrink to nothing but position counters, with no data-handling code of its own.
