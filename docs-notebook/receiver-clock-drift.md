# Receiver clock drift on an SDRplay RSP1B

`RtlSdrSource.clock_drift_seconds` compares the span of block arrival times against
the audio those blocks carry.  A warning fires when the two move apart by more than
`_DRIFT_PPM_LIMIT`.  On an RSP1B the warning arrived every few minutes, always
negative, with nothing in the log before it.  This document records what that turned
out to be.

## What was measured

Date: 2026-09-18.  Receiver: SDRplay RSP1B on a rooftop antenna, tuned to 3530 kHz.
Host: Windows 11, the same machine the monitor runs on.  The figures come from
`_warn_about_drift`, which reports every interval at DEBUG and warns only past the
limit.  Before this run it reported only the warnings, so the intervals around one
had never been seen.

Eleven consecutive intervals of 60 seconds, starting from a baseline of -45 ms:

|---|---|---|
| 20:03:30 | +10.4 ms | +10.4 ms |
| 20:04:31 | +9.5 ms | +19.9 ms |
| 20:05:31 | -17.1 ms | +2.8 ms |
| 20:06:31 | +15.8 ms | +18.6 ms |
| 20:07:31 | +11.2 ms | +29.8 ms |
| 20:08:31 | -11.5 ms | +18.3 ms |
| 20:09:31 | +29.8 ms | +48.1 ms |
| 20:10:31 | -52.3 ms | -4.2 ms |
| 20:11:31 | -9.7 ms | -13.9 ms |
| 20:12:31 | +12.2 ms | -1.7 ms |
| 20:13:31 | +5.4 ms | +3.7 ms |

The warning fired on the 20:10:31 row alone.  The three rows after it are routine.

## What it rules out

**The sample rate is sound.**  The cumulative figure over eleven minutes came to
+3.7 ms, which is 5.6 ppm and the order a crystal gives.  A rate error accumulates
instead of returning to zero, so this run puts a ceiling on any such error far below
the limit.  This matters because
`SdrplayDevice._configure` returns the rate that was asked for and never reads back
what the synthesizer settled on, where `RtlSdrDevice._configure` does read back and
warns.  That asymmetry remains, and it is not the cause of these warnings.

**The warnings are not noise crossing the limit.**  The nine routine intervals have a
mean of +2.9 ms and a standard deviation of 12.2 ms, so the 30 ms limit sits 2.22
sigma up and 2.69 sigma down.  Some crossings from noise alone are therefore expected.
A crossing of that kind reads 30 to 40 ms
and takes either sign.  The observed warnings read -45, -52, -55 and -61 ms and were
all negative, which a symmetric process grazing its limit does not produce.

## What it shows

The interval before the warning read **+29.8 ms** and the warning read **-52.3 ms**.
A stall conserves blocks: the interval that loses them reads positive and the
interval that gets them back reads negative.  The pair is that signature, and the
cumulative figure returning to zero confirms no sample was lost or gained.

The two halves are not equally visible, and that is why the fault looked causeless.
A stall spreads its withholding over however many intervals it straddles, so the
positive halves are diluted, where the catch-up burst is instantaneous and falls
wholly inside one interval.  Here the positive half reached +29.8 ms against a 30 ms limit
and missed warning by 0.2 ms.  Three earlier reports had no positive beside them for
the same reason.

## The first change to the message

The wording said the measurements were suspect on both signs.  Nothing is lost when a
buffer empties, and the analyzer counts samples at the nominal rate rather than reading
arrival times, so no measurement downstream can tell that it happened.  That clause
moved to the loss case, where samples did go missing.

`_warn_about_drift` also began reporting every interval at DEBUG.  One interval cannot
show what a negative figure is, and only the quiet intervals around a warning carry
that.  Every table in this document below this point exists because of that one line.

## The forced collection in the plotter

`buzz.plotter._gc_guarded` disables collection around a chart render, to work around a
PySide crash, and then forces a collection, to work around a matplotlib leak.  The two
workarounds are unrelated and only share a decorator.  Timing the forced collection
gave this, at 20:18 and 20:19 on the same date and machine:

| Collection | Objects freed | Duration |
|---|---|---|
| Daily chart | 9195 | 86.5 ms |
| Smoothed chart | 7526 | 73.4 ms |
| Daily chart, next minute | 9202 | 73.8 ms |
| Smoothed chart, next minute | 7814 | 65.4 ms |

That is about 160 ms per minute, on a cadence, in a process whose receiver callback is
Python and needs the GIL.

The first question was whether the forced collection is needed at all, since every
chart method already calls `plt.close(figure)`.  The counts answer it: about 8500
objects a render, so `plt.close` is not sufficient and the collection stays.

The second question was why a full collection costs that much.  It is the walk rather
than the freeing.  Every object the render made is still in generation 0, because
`gc.disable()` runs for the whole render and nothing is promoted while collection is
off, so a generation 0 pass finds the same garbage without walking the old heap.
Measured on the development machine over five renders each, calling the undecorated
render:

| Pass | Objects freed | Duration |
|---|---|---|
| Full | 5707 | 19.63 ms |
| Generation 0 | 5707 | 1.96 ms |
| Generation 1 | 5707 | 2.10 ms |

Two changes followed.  `_gc_guarded` collects generation 0, and `buzz.main` calls
`freeze_startup_heap` before any thread starts, which moves the imports, the ring
buffer and the display into the permanent generation so that no later pass walks them.
Measured together on the running monitor at 20:25:

| Collection | Objects freed | Duration |
|---|---|---|
| Daily chart | 10258 | 4.0 ms |
| Smoothed chart | 7129 | 2.2 ms |

The counts held and the time fell from 160 ms a minute to 6.2 ms.  The two changes went
in together, so this does not say how much each contributed.

### What these timings do not say

They are wall-clock durations of the `gc.collect()` call, taken on the calling thread.
They bound the stall rather than measure it.  Marking and sweeping are C and do not
release the GIL, but a collection also runs finalizers and weakref callbacks, which are
Python, and the eval loop can switch threads there.  Some of the 86 ms may have been
yielded to another thread.  Python 3.13 also made automatic old-generation collection
incremental, where an explicit `gc.collect()` stays a full stop-the-world pass, so the
behavior differs between the development machine on 3.14 and CI on 3.12.

What the receiver actually lost is a different quantity: the largest gap between two
consecutive callbacks.  Nothing measures that yet.

## The stall model was wrong

Every section above reasons from `clock_drift_seconds`, which infers a stall from
arrival timestamps a minute apart.  A second measurement on the receiver side, reported
once a minute so that it sits in the log beside the drift figure for the same minute,
settles it.

The figures below came from a first version of that measurement, which took the
interval between two callbacks and subtracted the audio the delivery *before* it held.
That arithmetic is wrong for a library which pauses and then hands over what it
accumulated, because the large delivery arrives *after* the gap: every inter-burst
period read as lateness, and the 72 ms figure is the burst period rather than a stall.
`SdrplayDevice._note_the_backlog` replaced it, and measures elapsed time against audio
delivered, which no delivery size can fool.

The conclusion survives the correction, because it rests on the figure not moving with
the drift rather than on what the figure is.

Nine consecutive minutes on 2026-09-18, with the two lines paired:

| Minute | Drift | Worst wait | Waits past 10 ms | Past 100 ms |
|---|---|---|---|---|
| 20:50 | +20.2 ms | 72.3 ms | 954 | 0 |
| 20:51 | +21.9 ms | 72.6 ms | 955 | 0 |
| 20:52 | -10.7 ms | 73.0 ms | 953 | 0 |
| 20:53 | +9.6 ms | 74.7 ms | 954 | 0 |
| 20:54 | +2.0 ms | 72.8 ms | 953 | 0 |
| 20:55 | +1.5 ms | 72.7 ms | 954 | 0 |
| 20:56 | -3.3 ms | 86.6 ms | 952 | 0 |
| 20:57 | +22.3 ms | 71.6 ms | 953 | 0 |
| 20:58 | **-56.4 ms** | 74.4 ms | 956 | 0 |

The last row warned.  Its callback timing cannot be told apart from any other row.

The two quantities are independent, and both directions were seen.  Drift swung 32.6 ms
between two minutes whose worst wait moved 0.4 ms.  The worst wait moved 15.0 ms between
two minutes whose drift stayed inside its own noise.  Over the nine minutes the
correlation is -0.416 with p = 0.305.

A prediction was written down before the warning arrived: worst wait 72 to 76 ms, zero
waits past 100 ms, and 953 to 955 past 10 ms.  The warning minute gave 74.4 ms, zero,
and 956.

## What the drift excursions are

The cumulative figure, which no single interval shows, has the answer.  Two runs, one
before the garbage collection change and one after:

| Cycle | Minutes | Peak | Discharge | Ends at |
|---|---|---|---|---|
| Run 1, before the collection change | 8 | +48.1 ms | -52.3 ms | -4.2 ms |
| Run 2, first cycle | 9 | +63.5 ms | -56.4 ms | +7.1 ms |
| Run 2, second cycle | 8 | +48.7 ms | -59.4 ms | -19.2 ms |

Every cycle climbs for eight or nine minutes to between +48 and +64 ms, discharges the
lot in one interval of -52 to -59 ms, and starts again near zero.  Run 1 and run 2 sit
either side of the collection change, which altered this machine's behavior
substantially and left the cycle alone.

The third cycle was predicted before it happened, which is the reason to believe the
first two.  With the cumulative at +54.1 ms the prediction was a discharge within one or
two minutes, of -50 to -60 ms, with the worst callback wait still near 72 to 75 ms and
nothing past 100 ms.  It arrived on the second minute at -59.4 ms, with a worst wait of
74.0 ms and nothing past 100.  The cumulative came to -13.8 ms where the prediction
said within about 10 ms of zero.

The per-minute fill is lumpy where the average is not.  One cycle ran +13.6, +3.9,
+12.5, +1.9, +0.8 and +16.0 ms, which averages 7.6 ms a minute and matches the earlier
cycles, so the buffer fills in steps rather than smoothly.

Read with the callback measurement, that is a buffer filling and emptying.  A positive
minute means the device delivered less audio than the interval holds, so something is
holding audio back, at about 8 ms a minute or 130 ppm.  The discharge minute delivers
about 56 ms more than the interval holds, which is that buffer emptying.  No callback
waits longer than usual while it happens, so the extra samples arrive in ordinary
deliveries at the ordinary cadence.

Nothing is lost and nothing is late.  The buffer depth cycles between roughly zero and
56 ms, every seven or eight minutes, and the warning fires on the minute it empties.

## What actually holds the GIL

The receiver callback is a ctypes callback, so the library's thread has to acquire the
GIL to run it.  Anything that holds the GIL without yielding therefore delays capture.
Two suspects were measured, with a thread that sleeps 1 ms in a loop and records how
far past that sleep it overran.  An overrun is time somebody held the GIL, and a pure
Python holder cannot cause one, because the eval loop drops the GIL every
`sys.getswitchinterval()`, which is 5 ms by default.

A first version of that probe used a busy loop rather than a sleep.  It reported a
render taking 12 seconds, because the probe was itself competing for the GIL over a
hundred million times per render.  A probe that is the biggest consumer of the thing it
measures measures itself.

**Matplotlib does not hold it.**  Four renders of a 1440-point chart:

| Run | Drew in | Worst overrun | Overruns past 10 ms |
|---|---|---|---|
| Idle baseline | | 0.8 ms | |
| 0 | 104.2 ms | 8.1 ms | 0 |
| 1 | 80.9 ms | 7.2 ms | 0 |
| 2 | 77.9 ms | 8.1 ms | 0 |
| 3 | 79.0 ms | 7.9 ms | 0 |

A render takes 80 to 104 ms of wall time and yields throughout.  The longest anyone
waits is about 8 ms.  So rendering cannot explain a stall of tens of milliseconds, and
an earlier claim in this document that Agg's C++ holds the GIL through a draw was wrong.

**A cycle collection does hold it, for all of it.**  Against a heap of 400,000 objects
in cycles:

| Heap | Generation | Collection took | Worst overrun |
|---|---|---|---|
| Not frozen | 0 | 0.1 ms | 0.0 ms |
| Not frozen | 2 | 46.6 ms | 50.2 ms |
| Frozen | 0 | 0.1 ms | 0.0 ms |
| Frozen | 2 | 0.1 ms | 0.0 ms |

The overrun matches the collection's own duration, so nothing else runs for any of it.
That is the only mechanism measured all evening whose size matches the stalls, and
freezing removes it.

`gc.freeze()` costs nothing.  At 100,000, 400,000 and 800,000 objects it took under
0.01 ms and caused no overrun, because it splices generation lists rather than walking
them.  So it can be called again after the display exists, which matters: the first
call runs before any thread starts, which is before the Qt window is built, and a
window built after it would be walked by every automatic pass for the life of the
program.  `buzz.main.freeze_live_heap` is called twice for that reason, and collects
first so that freezing does not pin whatever garbage happens to be alive.

## What this changed in the program

The per-interval movement is the wrong signal on its own.  It measures buffer depth
changing as well as audio going missing, and only the second is a fault.

The sign carries the distinction, because audio cannot be created.  More audio than an
interval accounts for can only be audio that already existed arriving late, so a
negative figure is never a loss.  A positive one is ambiguous: audio is either missing
or being held, and the fill half of this cycle is eight or nine minutes of exactly that.
Only a total that keeps growing separates them.

| Reading | What it is |
|---|---|
| Negative | A buffer draining.  Never a loss. |
| Positive, small, and recovering | A buffer filling.  Not a loss either. |
| Positive, and the total keeps going | A loss nothing else reports. |

`RtlSdrPipeline._warn_about_drift` follows three rules from that.  A positive interval
past `_DRIFT_PPM_LIMIT` warns, which is the loss the check was written for.  A negative
interval reports at DEBUG and never warns.  A total that stands more than
`_CUMULATIVE_DRIFT_LIMIT_SECONDS` from its baseline warns once per excursion, in either
direction, with the sign choosing the message: a positive total sends the operator after
load, and a negative one after the configured sample rate.

The third rule adds detection rather than removing it.  A leak of 20 ms a minute never
crosses the per-interval limit and would corrupt every measurement the station takes,
and nothing in the program could see it before.  `_CUMULATIVE_DRIFT_LIMIT_SECONDS` is
300 ms, about five times the largest excursion measured here, so a buffer cycle cannot
reach it.  The rule stays quiet when the interval rule has already spoken about the same
minute, because a loss large enough to trip both is one event.

Two tests pin it.  `test_a_buffer_cycling_is_never_reported` drives three measured
cycles and asserts silence, and `test_a_leak_too_slow_for_one_interval_is_still_caught`
asserts the total finds what the interval cannot.

The collection work stands whatever caused the drift.  `buzz.plotter._gc_guarded`
collects generation 0 rather than the whole heap, which took the forced collections from
160 ms a minute to 6 ms, and `freeze_live_heap` takes the long-lived objects out of the
automatic passes as well.

## What the driver is probably doing

This is speculation, and it is recorded so that nobody repeats the reasoning from
nothing.  Nothing here is a reason to change this program.

The period, the depth and the rate mismatch are one fact rather than three.  If a
producer and a consumer run at slightly different rates against a bounded buffer, then
`period = depth / mismatch`.  The three cycles give:

| Cycle | Peak | Minutes | Implied mismatch |
|---|---|---|---|
| Run 1 | +48.1 ms | 8 | 100 ppm |
| Run 2, first | +63.5 ms | 9 | 118 ppm |
| Run 2, second | +48.7 ms | 8 | 101 ppm |

Those agree within about 20%, which supports the producer and consumer reading.

A second reading fits as well: a buffer emptied in fixed chunks, where a partial chunk
at the end is not emitted until it fills, and the accumulated remainder comes out in one
piece when it does.  That predicts a constant discharge, and the three discharges span
7.1 ms.  The drift figure is sampled on a 60 second window, though, and the discharge
minute also holds a normal minute's fill of about 8 ms placed wherever in that minute
the discharge fell.  So the measurement alone smears a constant discharge by roughly the
spread observed, and a fixed chunk size is not ruled out.

The lumpy fill fits that too.  One cycle ran +13.6, +3.9, +12.5, +1.9, +0.8 and +16.0 ms
against a steady 7.6 ms average, which is what a quantized release looks like sampled on
a window that does not align with it.

There are at least three layers that could do this: the device's own transport, the USB
stack, and the API library's buffering.  Each has its own quantum and its own clock, so
a composite is likely and none of it is visible from here.

**One experiment would separate the two readings, and needs no code.**  Run at a
different `iq_sample_rate`.  A buffer that is a fixed number of samples fills twice as
fast at twice the rate, so the period should roughly halve.  A chunk boundary measured
in time does not move.

## What is still open

**Whether an RTL-SDR does the same.**  One drift limit covers both receivers, and
nothing has paired these measurements on the other one.

**Why the buffer fills at all.**  `SdrplayDevice._configure` returns the sample rate
that was asked for and never reads back what the synthesizer settled on, where
`RtlSdrDevice._configure` does read back and warns.  That asymmetry should be closed
whether or not it explains the mismatch.
