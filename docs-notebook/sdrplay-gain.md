# What an SDRplay RSP1B does about gain

The original measurements used one unit on 2026-09-16, while listening at 3530 kHz.
Later sections give their own dates and conditions.  The frequency matters for the
gain conversion and may affect the sample levels too.

## The receiver reports its own gain, and the figure can be trusted

`gainVals.curr` is an output parameter the library fills in, and unlike an RTL-SDR
Blog V4, which answers 0.0 at every setting, an RSP answers with a number that moves.
`tools/sdr_gain_probe.py` read it at eleven settings spanning the whole ladder, and
this is what each implies for the receiver's gain before any reduction, once the
reduction written is added back:

    LNA state     0     0     0     0     1     2     4     4     5     6     6
    reduction    20    30    40    50    60    70    80    90   100   110   120
    reported   71.4  61.4  51.4  41.4  31.4  21.0  11.3   1.3  -8.5 -18.4 -28.4
    implied    91.4  91.4  91.4  91.4  91.4  91.0  91.3  91.3  91.5  91.6  91.6

Two things follow, and the second is the more useful.

The vendored LNA gain reduction table is right.  A wrong entry would put its own rows
somewhere other than within half a decibel of the rest, because the reported figure
and the table's prediction enter that sum from opposite directions.  Seven LNA states
agreeing to 0.6 dB is not something a wrong table produces.

And the receiver's gain is a fixed 91.4 dB less whatever reduction is set.  That is
what lets `buzz.sdrplay_device` state its ladder in real decibels, from +71 down to
-29, rather than as the negative of a reduction.  The figure is asked of the hardware
at open rather than assumed, because it is measured here at one frequency on one unit
and the conversion gain is not flat across HF.  The constant is the fallback for a
library that declines to answer.

## The delivered samples exceed the signed 14-bit range

At the top of the ladder the raw peak reached 13978, and at the bottom it sat around
22.  The larger value exceeds the signed 14-bit range of -8192 through 8191.

Interpretation reviewed on 2026-09-18: this rules out unchanged signed 14-bit counts,
but does not establish where the receiver overloads.  The API delivers signed 16-bit
values after filtering and decimation, so the output endpoints describe that format.
Those operations can move clipped values away from an endpoint.  Hardware overload
reports provide a separate indication that the gain probe must examine.

The [API 2.13 specification](https://www.sdrplay.com/docs/SDRplay_SDR_API_Specification.pdf),
section 3.52, describes left-justified 16-bit output.  Left alignment would multiply
a signed 14-bit count by four, without increasing the ADC resolution.
The installed API 3.15 guide, section 3.21, declares `short` sample buffers but does
not specify that alignment.  The older description suggests a scaling convention,
but does not establish the exact scaling of this decimated stream.

## The driver uses the signed 16-bit output range as its reference

Decision recorded on 2026-09-18: keep the SDRplay driver's normalization divisor at
32768, with output endpoints of -32768 and +32767.  These constants define our
API-output dBFS reference, not a measurement of ADC headroom or effective resolution.

We have not found an explicit SDRplay API 3.15 statement that guarantees this scaling
across devices and configurations.  The installed guide declares `short` buffers,
which establishes the storage type but does not establish the signal's full-scale value.
The older API description above provides historical support, not a current guarantee.

Independent observations support this convention.  The Northern Utah WebSDR author's
[RSP1A observations](https://www.sdrutah.org/info/observations_on_the_RSP1a_HF.html),
under "Raw I/Q format", describe the same signed 16-bit output range and populated
low bits with API 3.07.  Our RSP1B measurements with API 3.15 reached 32765, as
recorded below.  That exceeds the signed 14-bit range and agrees with the reported
convention, although it does not prove the scaling for every configuration.

Use this reference unless contrary evidence appears, then revisit the driver constants
and any affected level calculations.  Keep hardware overload reports separate from
output endpoint counts.  Neither populated low bits nor the normalization divisor
establishes 16 bits of effective resolution.

## The noise floor has a knee, and the sweep finds it

The same eleven readings, as the quiet level between bursts:

    gain      -28.4 -18.4  -8.5   1.3  11.3  21.0  31.4  41.4  51.4  61.4  71.4
    quiet     -73.5 -71.8 -73.1 -73.3 -70.6 -71.2 -65.2 -55.8 -45.6 -35.7 -26.5

Below about 21 dB of gain the level does not move: that is the converter's own noise,
and the antenna is not reaching it.  Above it the level tracks the gain within a
decibel, which is the antenna.  The knee between them is what `GainChooser` is looking
for, and on this antenna it sits between 21 and 31 dB.

## The chosen gain follows the antenna

Three sweeps, same receiver, same frequency, same day, with nothing changed but what
was on the far end of the coax:

    indoor rabbit ears                  24 dB
    the same, with a hand on them        8 dB
    rooftop antenna                    3.0 dB

A better antenna delivers more noise, so its noise overtakes the converter's at a
lower gain and the knee moves down.  The direction was predicted before the second and
third sweeps were run, which is what makes these three numbers evidence that the
chooser tracks the band rather than three numbers that can be explained afterwards.

The hand is worth more than it sounds: 16 dB, against 5 dB for the whole step from
there to a rooftop antenna.  A body coupled to a short indoor whip is a large change
to a poor antenna, where a rooftop antenna is already collecting most of what is
there.

None of this says what the right gain is for a station.  It says the sweep responds to
the antenna in the direction and roughly the amount it should, which is the part that
could have been silently wrong.

## What none of this covers

This covers one unit, one frequency, one day and one operator's roof.  The
conversion gain is measured rather than assumed at run time, so a second unit
costs nothing, but the LNA table is vendored and covers only the band below 50 MHz
on an RSP1B and 60 MHz on an RSP1A.  `buzz.sdrplay_device` refuses a tuning above
that edge rather than using the row it has.

Whether 32 dB of arc headroom suits an antenna this large is a separate question that
these measurements do not answer.  A rooftop antenna choosing 3.0 dB is close enough
to the bottom of the ladder to make it worth asking.

## Hardware overload without output endpoint hits

On 2026-09-18, the operator connected the rooftop antenna to the RSP1B for repeated
gain probes.  The monitor frequency was 3530 kHz, with a 50 kHz tuning offset.
The receiver therefore tuned to 3580 kHz and delivered 256,000 complex samples per
second after eightfold decimation from 2.048 MHz.

Each row collected 129,024 complex samples, or 258,048 individual I/Q values.
The probe requested half a second and read whole blocks of 2048 complex samples.
One ascending pass used a separate receiver session.  A second session ran ascending
and descending passes, starting at 15:20:23 UTC.  The last three gains gave:

| Requested gain | Quiet level across three captures | Raw peak across three captures | Hardware overload |
| --- | --- | --- | --- |
| 51 dB | -28.1 to -27.8 dBFS | 19290 to 19605 | None reported in all three |
| 61 dB | -18.2 to -18.0 dBFS | 32463 to 32673 | None reported in all three |
| 71 dB | -8.0 to -7.9 dBFS | 32761 to 32765 | Active in all three |

Every capture at every gain had zero exact endpoint hits.  The endpoints were -32768
and +32767.  The hardware report therefore detected overload that endpoint counting
missed.  On the descending pass, the report cleared when gain decreased from 71 to
61 dB.  The detection count stayed at one across both 71 dB captures, so a count
change alone would have missed the continuing overload.

The 61 dB captures still had peaks near the output limit.  Their complex peak levels
were +0.5 to +0.6 dBFS, compared with -4.5 to -4.0 dBFS at 51 dB gain.
The smaller peak increase is a reason to investigate compression, but changing signals
prevent a firm conclusion.  No hardware report does not establish that a capture has
no distortion, or that a later transmission will fit.

A pure two-bit left shift of signed 14-bit counts produces multiples of four.
The observed peak of 32765 is not a multiple of four, so these are not unchanged
left-shifted ADC counts.  Subsequent processing can account for lower bits, but these
measurements do not identify the API's exact scaling or filtering.

### Repeated overload checks in gain selection

The gain sweep now treats one hardware report as a reason to check again.  It reads
two more intervals at the same gain and imposes a hard bound only when at least two
of the three intervals report overload.  The two confirmation intervals do not enter
the noise-floor fit, peak, or endpoint count, because only gains that overload receive
them.  The two-out-of-three rule is a policy choice for distinguishing a brief event
from continuing overload, not a measured optimum.

A live sweep on 2026-09-18 used the rooftop antenna at 3530 kHz with the same 50 kHz
tuning offset and 256 kHz output rate.  Both normal measurements at 71 dB triggered
confirmation.  All six intervals reported overload, producing two confirmed results.
The two normal measurements at 61 dB produced no hardware reports.  Their maximum
delivered levels were 0.6 dBFS at 71 dB and 0.0 dBFS at 61 dB.

The sweep chose 8 dB from the fitted noise-floor knee.  Its 32 dB reserve independently
put the headroom bound at 41 dB, so the confirmed overload at 71 dB did not change this
answer.  The run still exercised the new distinction: clear gains received only their
normal intervals, while consistent overload received both checks and became evidence.

At the same time, the operator described the monitor's narrow-channel reading as an S5
noise floor and an S6 120 pps signal, with little noise on the band.  That observation
does not identify what overloaded the wider receiver path at 71 dB.  It does show that
the confirmed overload did not require a particularly loud 120 pps signal in the
channel the monitor was measuring.

Two more sweeps on 2026-09-18 changed only the monitoring frequency.  The 1550 kHz run
put KZDG, a local AM station the operator knows will overload this receiver, inside the
captured span.  The lowest gains with confirmed overload were:

| Monitoring frequency | Chosen gain | Reserve bound | First confirmed overload | Delivered peak there |
| --- | ---: | ---: | ---: | ---: |
| 3530 kHz | 8 dB | 41 dB | 71 dB | +0.6 dBFS |
| 1800 kHz | 8 dB | 42 dB | 52 dB | -14.9 dBFS |
| 1550 kHz, KZDG | 8 dB | 8 dB | 32 dB | +0.3 dBFS |

Every entry in the first-confirmed-overload column reported overload in all six
intervals: two normal passes and two retries after each.  The 1800 kHz result is the
clearest separation between the two indications.  Hardware reported continuing
overload while the delivered samples remained almost 15 dB below API-output full
scale.  Endpoint proximity therefore cannot replace the hardware report.

The reserve bound was at or below the first confirmed overload in all three runs, so
hardware evidence did not lower any chosen gain.  It still guards configurations where
the quiet-level reserve would otherwise allow a gain that the receiver repeatedly
reports as overloaded.

Just before the antenna move, the operator reported about -84 dB signal and -93 dB
noise floor on the other receiver.  These were not simultaneous measurements.
The probe measures wideband I/Q in dBFS, so its figures cannot directly establish an
offset against those monitor readings.  No calibration setting changed during these
tests.

## Overload clearance during API shutdown

The first live probe on 2026-09-18 stopped before its first row because an overload
acknowledgement returned the API's "not initialized" error.  A trace located the clearance
event inside `Uninit`, during the brief startup used to learn the receiver's gain.
The API had already stopped accepting `Update`, but the driver saved that failure
and reported it during the next capture.

The driver now accepts overload events before calling `Init` and stops accepting them
before `Uninit`.  A new stream starts with a clear active state and retains the
device's detection count.  Shutdown can also race an acknowledgement already in
progress, so that path must not save a capture error after shutdown starts.
Acknowledgement failures while capture continues still make overload readings fail.

Tests deliver events from inside both API lifecycle calls and simulate shutdown during
acknowledgement.  Both completed probe sessions released the receiver.  The second
session reopened it without a shutdown acknowledgement failure.

## Initial level calibration estimate

On 2026-09-18, sequential comparisons against a calibrated RTL-SDR gave these settings
for one RSP1B on 3540 kHz:

| SDRplay gain | Offset that matched the RTL-SDR | Offset plus gain |
| ---: | ---: | ---: |
| 7 dB | +6 dB | 13 dB |
| 13 dB | -2 dB | 11 dB |
| 19 dB | -8 dB | 11 dB |

The adjustable gain behaved one for one at 13 and 19 dB.  The 7 dB result was close to
the fitted noise-floor knee, where receiver self-noise still affected the reported
level.  The gain chooser therefore adds 6 dB to the knee for this device, unless the
headroom bound requires less.  Its uncalibrated starting offset is `-gain_db + 11`.
The RTL-SDR retains the knee itself and `-gain_db`.  Each device class owns both its
post-knee padding and its offset estimate.  A measured calibration still replaces the
estimate.

An earlier comparison at 17 dB suggested an 8.5 dB intercept from signal and floor
differences of 7.82 and 8.98 dB.  The later two-point check was internally consistent,
while none of these readings were simultaneous because the antenna had to move between
receivers.  The implementation uses 11 dB and records the earlier disagreement rather
than treating either measurement as exact.

This is evidence from one RSP1B, one RTL-SDR, and one station.  It is a starting value
for a new configuration rather than a claim about every unit.
