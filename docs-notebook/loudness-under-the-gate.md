# Loudness below BS.1770's absolute gate

Measured on 2026-09-19, against ffmpeg's `ebur128` filter from the
`ffmpeg-2022-02-28-git-7a4840a8ca-essentials_build` build on this machine.

## The question

`--playback-gain auto` applied no gain to recordings from this station, so a render
came out inaudible.  The code read the meter's answer as silence.  The question was
whether the recordings really are silent, and if not, what the meter was saying
instead.

## What the meter does with a quiet file

BS.1770 measures integrated loudness in two gated passes.  The first discards every
400 ms block under an absolute gate of -70 LUFS.  The mean of the blocks that survive
cannot come out below the gate that admitted them, so the integrated figure a meter
reports is either at or above -70 LUFS, or it is the meter saying it has nothing.

`ebur128` says it has nothing by printing exactly -70.0, or -inf.  Sine tones of 15 s
at 16 kHz, each measured on its own:

| tone level | integrated | true peak |
|---|---|---|
| -30 dBFS | -51.0 LUFS | |
| -60 dBFS | -70.0 LUFS | -77.9 dBTP |
| -75 dBFS | -70.0 LUFS | -89.1 dBTP |
| -85 dBFS | -70.0 LUFS | -inf |
| -95 dBFS | -70.0 LUFS | |
| 15 s of digital silence | -70.0 LUFS | -inf |
| 0 s file | -70.0 LUFS | -inf |

Two conclusions follow, and the second is the useful one.

No threshold under -70 LUFS can ever be reached, so a sentinel placed there fires only
on -inf.  A sentinel at -86 LUFS was tried and is what prompted these measurements: it
left 15 s of digital silence reporting `is_effectively_silent = False`, and a
zero-length file was given +43.99 dB.

The integrated figure cannot separate an empty file from a quiet one, and the true
peak separates them exactly.  A -85 dBFS sine quantizes to all zeros in int16 and so
is empty in fact, which is why it reads -inf beside the -75 dBFS tone's -89.1 dBTP.

## Recovering the loudness

Loudness is a ratio, so lifting a file by a constant moves its integrated figure by
that same constant.  The lift can therefore be applied before the meter and subtracted
from its answer.  Measured on the event above, at five probe gains:

| probe gain | measured | implied true loudness |
|---|---|---|
| +20 dB | -57.29 LUFS | -77.29 LUFS |
| +30 dB | -47.29 LUFS | -77.29 LUFS |
| +40 dB | -37.29 LUFS | -77.29 LUFS |
| +50 dB | -27.29 LUFS | -77.29 LUFS |
| +60 dB | -17.29 LUFS | -77.29 LUFS |

The recovered figure is identical across a 40 dB span, to the resolution ffmpeg
prints.  Applying the lift inside the filter chain, as `volume=63.8dB,ebur128`, agrees
with the same measurement taken from an amplified file written to disk.  `volume`
works in floating point whatever the input format, so a lift that takes the peak to
the ceiling does not clip on the way to the meter.

`buzz.loudness.measure` uses the true-peak ceiling as the lift, because that is the
loudest this program would make the file in any case.  A file that still reads nothing
when lifted that far holds too little for R128 to describe, and falls back to the peak.

## Why not answer from the peak alone

The first fix tried was to drop the loudness target for these files and take the
true-peak ceiling as the gain.  It is simpler and it needs no second pass.  Measured on
the same event, it overshoots:

| approach | gain | resulting loudness |
|---|---|---|
| ceiling alone | +63.80 dB | -13.49 LUFS |
| recovered target | +54.29 dB | -22.99 LUFS |

The target is -23 LUFS, so the ceiling alone comes out 9.5 dB hot.  The reason is the
crest factor.  This content measured 0.4 LU of loudness range, because an arc at this
level is closer to continuous noise than to a train of isolated bursts, so there is
almost no gap between its peak and its mean for the ceiling to leave room in.  The
figure is content-dependent, which means a fallback of this kind cannot be corrected
by a constant either.
